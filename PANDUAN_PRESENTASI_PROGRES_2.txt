================================================================================
PANDUAN PRESENTASI — PROGRES 2 : "PERAN SETIAP PENGGUNA"
Sistem Manajemen Gym Multi-Tenant (Laravel)
================================================================================

Dokumen ini dibuat berdasarkan pembacaan menyeluruh terhadap kode project:
routes/web.php, semua controller, model, migration, seeder, dan tampilan (blade).
Gunakan sebagai "naskah contekan" latihan — bukan untuk dibaca langsung saat demo.

--------------------------------------------------------------------------------
A. PITCH PEMBUKA (hafalkan 1 kalimat ini)
--------------------------------------------------------------------------------
"Project ini adalah sistem manajemen gym berbasis web dengan model SaaS
(Software as a Service). Satu aplikasi dipakai oleh banyak pemilik gym
(tenant), dan setiap orang di dalam gym — pemilik, admin, manager,
resepsionis, personal trainer, sampai member — punya halaman dan peran
masing-masing yang berbeda. Pada progress 2 ini saya fokus menyelesaikan
peran dan fitur dari setiap pengguna tersebut."

Kalau guru minta versi lebih teknis:
"Secara teknis: Laravel 12 + MySQL, konsep multi-tenant satu-database
(pemisahan data lewat kolom tenant_id), autentikasi session Laravel, dan
role disimpan di tabel users sebagai string (superadmin, owner, admin,
manager, receptionist, trainer, member). Setiap role login diarahkan ke
dashboard-nya sendiri."

--------------------------------------------------------------------------------
B. GAMBARAN BESAR (kalau guru tanya "project apa ini, siapa user-nya?")
--------------------------------------------------------------------------------
Masalah yang dipecahkan:
  Pengelolaan gym biasanya berceceran: daftar member di buku, kasir manual,
  jadwal kelas di grup chat, loker dicatat kertas. Pemilik beberapa cabang
  gym juga butuh satu sistem terpusat.

Solusi:
  1 platform yang bisa disewa banyak gym (multi-tenant). Tiap gym punya
  "tenant" sendiri dengan nama & domain sendiri (contoh: fitlife.workout.id).
  Di dalam satu tenant, semua orang di gym pakai aplikasi yang sama tapi
  melihat antarmuka sesuai perannya.

Pelaku / role di sistem (ini inti presentasi progress 2):
  1. Superadmin      -> pemilik PLATFORM (pihak penyedia software)
  2. Owner           -> pemilik GYM / tenant (melihat bisnisnya)
  3. Admin           -> pengelola operasional harian gym
  4. Manager         -> kepala operasional (alat, shift, approval)
  5. Resepsionis     -> front desk (tamu, loker, shift, keluhan)
  6. Personal Trainer-> pelatih (jadwal kelas & sesi PT)
  7. Member          -> anggota gym (self-service portal)
  8. Guest           -> pengunjung yang belum daftar (buku tamu / checkout publik)

Alur besar sistem (ceritakan seperti ini biar nyambung):
  Superadmin mendaftarkan tenant + memilih paket (Basic/Pro/Enterprise)
  -> tenant aktif -> Owner & staf gym login -> Admin bikin akun staf dengan
  role tertentu -> Resepsionis layani tamu/member di front desk ->
  Member akses portal sendiri (loker, kelas, PT, tagihan) -> Manager
  menyetujui operasional (void, cuti, komplain) -> Owner pantau semuanya
  read-only.

--------------------------------------------------------------------------------
C. KONSEP KUNCI YANG HARUS LU PAHAMI (biar gak gugup ditanya)
--------------------------------------------------------------------------------
1. Multi-tenant = banyak "perusahaan/gym" pakai 1 aplikasi. Di kode:
   hampir semua tabel punya kolom tenant_id, dan tiap query di controller
   selalu difilter `->where('tenant_id', $tenantId)`. Data antar-gym
   tidak tercampur.
   Bonus baru: tiap tenant punya halaman WEBSITE PUBLIK sendiri di
   subdomain (contoh demo: fitlife.localhost & powerhouse.localhost).
   Controller mencocokkan slug subdomain -> tenant, lalu menampilkan
   konten landing milik tenant itu saja.

2. Role & alur login: LoginController.login() mengecek kolom role user lalu
   me-redirect ke dashboard masing-masing, contoh:
   - superadmin  -> /superadmin/dashboard
   - owner       -> /owner/dashboard
   - admin       -> /admin/dashboard
   - manager     -> /manager/dashboard
   - receptionist-> /receptionist/dashboard
   - trainer     -> /trainer/dashboard
   - member      -> /member/dashboard
   Session di-regenerate setelah login (anti session-fixation), password
   di-hash, logout meng-invalidate session.

3. Arsitektur MVC Laravel (jawab cepat kalau ditanya):
   - routes/web.php      : daftar URL + controller mana yang menangani
   - Controller          : logika bisnis (validasi, simpan data, redirect)
   - Model (Eloquent)    : representasi tabel + relasi (User, Tenant, Member...)
   - Migration           : "blueprint" pembuatan tabel
   - Seeder              : pengisi data contoh/demo (DatabaseSeeder.php)
   - View (Blade)        : tampilan HTML
   Jadi alurnya: URL -> route -> controller -> model -> database, lalu
   controller kirim data ke view -> tampil ke browser.

4. RBAC = Role-Based Access Control: pembatasan menu berdasarkan peran.
   Di project ini role ditentukan lewat helper di model User
   (isAdmin(), isManager(), dst) dan dipakai untuk: redirect setelah login,
   menampilkan/menyembunyikan tombol di tampilan (misal Owner tidak melihat
   tombol Tambah/Hapus karena read-only), dan isi sidebar.

--------------------------------------------------------------------------------
F. POIN "NILAI PLUS" TEKNIS (sebutkan kalau ada waktu / biar guru terkesan)
--------------------------------------------------------------------------------
- Arsitektur multi-tenant: satu aplikasi, data dipisah per tenant_id.
- Pemisahan peran: tiap role punya prefix URL sendiri (superadmin/,
  admin/, manager/, receptionist/, trainer/, member/, owner/).
- RBAC lewat helper role (isAdmin, isManager, ...) — dipakai untuk
  redirect login, isi menu, dan menyembunyikan tombol (owner read-only).
- Sinkronisasi akun staf → profil role otomatis saat admin membuat akun.
- Anti double-booking loker (status + validasi 1 sewa aktif per member).
- Booking PT bebas konflik (cek jadwal trainer per tanggal & jam).
- Waitlist kelas dengan auto-promote saat ada yang batal.
- Penalti no-show member (block sementara dari RSVP kelas).
- Audit log / system log aktivitas penting (siapa, kapan, IP).
- Anti session-fixation: session di-regenerate setelah login.
- Semua halaman login/logout pakai mekanisme auth standar Laravel
  (CSRF token aktif di form, password ter-hash).
- Seeder lengkap → data demo realistis (member mendekati kedaluwarsa,
  alat perlu servis, komplain open) sehingga demo terasa hidup.
- Login DI-RATE-LIMIT (BARU): maks 5 percobaan gagal per email+IP,
  lalu dikunci 60 detik — anti brute-force. Hitungan otomatis bersih
  saat login sukses.
- Verifikasi email WAJIB untuk akun staf baru (BARU): link signed URL
  60 menit (tidak bisa dipalsukan), user diarahkan ke halaman verifikasi,
  kirim ulang link di-throttle, semua dashboard dijaga middleware
  'verified'. Admin otomatis kirim link saat membuat akun + badge status
  verifikasi di daftar staf.
- Landing page publik per tenant lewat SUBDOMAIN (BARU):
  {slug}.localhost → route `{slug}.{apex}` (apex bisa diganti per
  produksi, mis. workout.id). Satu template default, konten & warna
  mengikuti pengaturan tiap tenant.
- GATING PAKET DI SERVER (BARU, mulai menutup kelemahan #4): level
  kustomisasi landing ikut paket — Basic=teks, Pro=+warna/bagian/fitur,
  Enterprise=+statistik. Field di luar paket yang dikirim lewat request
  DIABAIKAN controller (terbukti lewat test otomatis).
- FITUR LUPA PASSWORD ala standar industri (BARU): token acak
  sekali-pakai tersimpan ter-hash, kedaluwarsa 60 menit, anti
  user-enumeration (respons sama untuk email terdaftar/tidak), throttle
  pada endpoint reset, sesi lama + cookie remember-me dimatikan setelah
  reset. Email dikirim tanpa campur tangan admin.
- Demo email memakai Mailpit (SMTP palsu): email reset muncul di inbox
  browser http://localhost:8025 — realistis tanpa butuh SMTP asli.
- Toggle lihat password (blind eye, icon eye/eye-slash icomoon) di semua
  form password: reset-password, forgot-password, login, dan member
  settings.
- Pengujian otomatis SUDAH berjalan: 37 test lulus, mencakup lupa
  password, member settings, rate-limit login, verifikasi email, landing
  subdomain + gating paket, LOGIN-PER-ROLE (7 role → dashboard sendiri),
  ANTI DOUBLE-BOOKING LOKER, dan WAITLIST KELAS + auto-promote. Test
  memakai database terpisah petgym_test — aman, tidak menyentuh data
  demo. Catatan menarik: test waitlist menemukan 1 BUG beneran (lihat
  bagian H poin 7) yang langsung diperbaiki.

--------------------------------------------------------------------------------
G. PERTANYAAN KRITIS YANG MUNGKIN DITANYA GURU + ARAH JAWABAN
--------------------------------------------------------------------------------
1. "Apa bedanya project ini dengan CRUD biasa?"
   -> Ada konsep multi-tenant (banyak gym dalam satu aplikasi, data
      terpisah) dan multi-role (tiap pengguna lihat antarmuka berbeda
      dengan kewenangan berbeda), plus alur approval (void butuh
      persetujuan manager, cuti butuh approval).

2. "Bagaimana kamu memisahkan data antar gym (tenant)?"
   -> Kolom tenant_id di hampir semua tabel; setiap query di controller
      selalu difilter tenant milik user yang login. Contoh nyata bisa
      ditunjuk di kode: di MemberPortalController / TrainerController,
      semua query diawali `where('tenant_id', ...)`.

3. "Bagaimana kamu mencegah manager masuk ke halaman admin?"
   -> Jawaban JUJUR: saat ini pembatasan utama ada di antarmuka — sidebar
      dan tombol disesuaikan per role, dan login diarahkan ke dashboard
      masing-masing. Belum ada middleware pembatas role di tiap grup
      route (hanya auth). Ini kelemahan yang saya sadari dan rencana
      perbaikannya adalah middleware role: misal `role:admin` pada grup
      /admin (lihat bagian H — sampaikan ini sebagai rencana, jangan
      mengaku sudah aman).

4. "Apa itu middleware? Apa bedanya role dan permission?"
   -> Middleware = penjaga di depan route (diproses sebelum masuk
      controller), misal memastikan user sudah login. Role = jabatan
      (admin, manager). Permission = aksi spesifik (misal 'menyetujui
      void'). Project ini memakai role sederhana; permission per-aksi
      adalah pengembangan lanjutan.

5. "Kenapa pilih Laravel?"
   -> Sudah menyediakan auth, ORM (Eloquent), migration, seeder, CSRF,
      session — jadi fokus ke logika bisnis. Juga populer di industri dan
      dokumentasinya lengkap.

6. "Kenapa password semua '1234'?"
   -> Itu hanya untuk akun demo di seeder supaya gampang dipresentasikan;
      password tetap disimpan ter-hash di database. Keamanan akun lain
      SUDAH lengkap: lupa password (reset sendiri via email), verifikasi
      email wajib untuk akun baru, dan login di-rate-limit (5x gagal =
      kunci 60 detik). Yang tersisa: kebijakan kekuatan password / 2FA.

7. "Pembayarannya asli gak?"
   -> Jujur: belum. Semua transaksi langsung dianggap lunas (simulasi
      metode 'qris'). Rencana: integrasi payment gateway. Kalau guru tanya
      "kenapa?" jawab: fokus progress ini adalah alur dan peran pengguna,
      bukan integrasi pihak ketiga.

8. "Bagaimana kalau dua orang sewa loker yang sama bersamaan?"
   -> Status loker dicek & diubah di database sebelum transaksi dicatat
      (loker "tersedia" baru bisa disewa), plus aturan 1 member = 1 sewa
      aktif. Diakui: belum pakai transaksi/locking database tingkat lanjut
      (race condition teoritis tetap ada) — pengembangan ke depan.

9. "Bagaimana kalau trainer sudah di-booking di jam yang sama?"
   -> Sistem cek dulu: booking dengan trainer, tanggal, dan jam yang sama
      yang masih berstatus 'scheduled' → kalau ada, booking ditolak dan
      member diminta pilih jam lain.

10. "Apa fungsi penalti no-show itu?"
    -> Member yang mendaftar kelas tapi tidak hadir tanpa pembatalan
      dicatat no_show_count; kalau melanggar, akunnya diblokir sementara
      dari pemesanan kelas (penalty_blocked_until). Tujuannya: kuota kelas
      tidak terbuang sia-sia.

11. "Owner kok cuma bisa lihat? kenapa?"
    -> Pemilik gym butuh pantauan performa, bukan operasional harian.
      Sengaja dibuat read-only supaya tidak bisa mengubah data yang
      dikerjakan stafnya (pemisahan tugas). Di kode: tombol ubah/hapus
      disembunyikan saat role owner.

12. "Siapa yang mengerjakan bagian mana — kamu sendiri?"
    -> Jangan berbohong dan jangan mengaku semua sendiri kalau tidak.
      Format jujur: "Saya yang merancang konsep, struktur database,
      alur fitur, dan menulis logika utama. Untuk beberapa bagian teknis
      (debugging, merapikan kode, kode berulang) saya dibantu tool AI
      (misal untuk generate CRUD), dan saya memahami serta bisa
      menjelaskan setiap bagian yang saya pakai." Guru lebih menghargai
      pemahaman + kejujuran daripada klaim muluk.

13. "Kenapa datanya banyak / ini data asli?"
    -> Semua data contoh dibuat oleh seeder (DatabaseSeeder.php) supaya
      demo realistis. Bukan data gym sungguhan.

14. "Apa rencana kamu selanjutnya?"
    -> (1) Middleware otorisasi per role, (2) lengkapi peran trainer,
      (3) payment gateway asli, (4) penegakan fitur paket untuk MENU &
      route aplikasi (contoh gating landing page sudah jalan di server),
      (5) kebijakan password kuat & 2FA opsional, (6) bersihkan
      file-file sampah di repo, (7) perluas test otomatis.

15. "Gimana cara kerja fitur lupa password kamu? aman gak?"
    -> Alur: user masukkan email → sistem bikin token acak sekali-pakai
      yang disimpan TER-HASH dan dikirim lewat email (link) → user buka
      link, set password baru → token langsung dihapus & semua sesi lama
      dimatikan. Aman karena: token tidak pernah tersimpan plaintext
      (DB bocor pun tak berguna), kedaluwarsa 60 menit, sekali pakai,
      respons sama untuk email terdaftar/tidak (anti user enumeration),
      dan endpoint-nya di-throttle. Email dikirim tanpa campur tangan
      admin — pemilik akun membuktikan kepemilikan lewat email, bukan
      admin yang menentukan password.

16. "Kok akun staf baru harus verifikasi email dulu? ribet."
    -> Ini standar industri (Google Workspace, Notion, semua SaaS
      serius). Fungsinya: (1) memastikan email yang didaftarkan admin
      benar-benar milik orang itu — kalau typo, link nyasar & akun tak
      aktif, (2) mencegah pembuatan akun palsu massal, (3) kalau nanti
      lupa password, email itu jadi jalur pemulihan yang aman. Teknisnya:
      link bertanda tangan (signed URL) yang kedaluwarsa 60 menit dan
      tidak bisa dipalsukan; akun yang belum verifikasi tidak bisa
      membuka dashboard mana pun.

17. "Kenapa tiap tenant punya website sendiri? itu jalan gimana?"
    -> Karena ini SaaS, tiap gym adalah "brand" sendiri — landing page
      adalah wajah publiknya. Teknis: route memakai subdomain
      ({slug}.localhost saat demo; di produksi tinggal ganti apex jadi
      workout.id → fitlife.workout.id). Subdomain dicocokkan ke tabel
      tenants lewat kolom slug, lalu menampilkan konten milik tenant
      itu. Kerennya: seberapa banyak yang boleh dikustomisasi MENGIKUTI
      PAKET — Basic hanya teks, Pro tambah warna/bagian/fitur,
      Enterprise tambah statistik. Dan penegakannya di server: request
      yang mengirim field di luar paket diabaikan controller (ada
      test-nya).

H. KELEMAHAN PROJECT (sadar diri = nilai plus di mata guru)

Urut dari yang paling penting. Sampaikan dengan tenang:
"Saya sudah mengidentifikasi kekurangan berikut, dan ini rencana perbaikannya."

   Ada file-file di luar aplikasi yang tidak berkaitan: folder

- Pastikan .env mengarah ke database yang benar, lalu jalankan sekali:
    php artisan migrate:fresh --seed
  (mengosongkan + mengisi ulang data demo — aman, ini database lokal).

  PENTING: buka lewat "localhost", BUKAN 127.0.0.1 — supaya subdomain

  diarahkan ke /admin/dashboard — jangan bingung kalau role lain diredirect.
- Buka tiap akun di mode incognito/private window yang berbeda, ATAU

- Jangan demo fitur yang belum pernah dicoba; minimal jalankan ulang
  seluruh skenario sehari sebelum presentasi. Ada baiknya minta teman

  lalu lanjut ke fitur lain.
- Sebelum presentasi, cek sekali bahwa sidebar tiap role tidak menampilkan
  menu yang kosong/rusak.
- PENTING (Windows): komputer ini punya variabel environment sistem
  MAIL_* dan DB_* yang MENIMPA isi .env (Dotenv Laravel immutable).
  Akibatnya: mau .env ditulis apa pun, Laravel tetap pakai nilai sistem.
  Solusi sebelum `php artisan serve` / `db:seed` / `tinker`:
      unset MAIL_MAILER MAIL_HOST MAIL_PORT MAIL_USERNAME MAIL_PASSWORD MAIL_SCHEME MAIL_FROM_ADDRESS MAIL_FROM_NAME
  (kalau mau permanen: hapus variabel MAIL_* / DB_* dari Environment
  Variables Windows — System Properties -> Environment Variables ->
  User & System variables -> Delete yang namanya mulai MAIL_/DB_, lalu
  buka ulang terminal. Nilai yang benar sudah ada di .env.)

   storage/logs/laravel.log dan link bisa dibuka dari sana. Kurang seru
   untuk presentasi, tapi tetap jalan.)

K. ISTILAH YANG WAJIB BISA DIJELASKAN (hafalkan satu kalimat masing-masing)
--------------------------------------------------------------------------------
- SaaS (Software as a Service): software yang disewa, bukan dibeli sekali.
- Multi-tenant: satu aplikasi melayani banyak pelanggan/gym.
- Tenant: satu "penyewa" = satu gym beserta datanya.
- RBAC: pengaturan akses berdasarkan peran pengguna.
- Middleware: lapisan penjaga sebelum request masuk ke halaman.
- MVC: Model (data), View (tampilan), Controller (logika) — pola Laravel.
- Eloquent ORM: cara Laravel berbicara ke database lewat objek PHP.
- Migration: cetak biru/perubahan struktur tabel yang bisa dijalankan ulang.
- Seeder: pengisi data awal/demo.
- Session: penyimpanan status login di sisi server (cookie berisi ID).
- CSRF: perlindungan form dari serangan situs silang (default Laravel).
- Auth: autentikasi (siapa kamu) — beda dengan otorisasi (boleh apa).
- Invoice/void: tagihan; void = pembatalan transaksi (di sini butuh
  persetujuan manager).
- No-show: member tidak hadir tanpa membatalkan pendaftaran.
- Waitlist: daftar tunggu; otomatis naik kalau ada slot kosong.
- Token reset: kode rahasia sekali pakai (tersimpan ter-hash) untuk
  membuktikan pemilik akun saat ganti password lewat email.
- SMTP: protokol pengiriman email; di demo memakai Mailpit (SMTP palsu)
  supaya email tampil di browser tanpa kirim beneran.
- User enumeration: teknik hacker mendeteksi email terdaftar; dicegah
  dengan respons seragam pada form lupa password.
- Rate limiting: pembatasan jumlah percobaan (di sini: 5x login gagal
  = kunci 60 detik) untuk mencegah brute-force.
- Signed URL: link bertanda tangan rahasia aplikasi yang tidak bisa
  dipalsukan & punya masa berlaku (dipakai di link verifikasi email).
- Slug/subdomain: nama unik tenant untuk alamat web, mis. "fitlife"
  pada fitlife.localhost / fitlife.workout.id.
